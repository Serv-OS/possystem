2 · Technical due diligence

2.1 Executive summary

ServOS is a multi-tenant, multi-device SaaS point-of-sale and operations platform for hospitality. A single React codebase (~100k+ lines) serves ~17 product surfaces — counter POS, bar, table service, kitchen display, self-service kiosk, mobile POS, time clock, online ordering, QR table ordering, loyalty portal, gift cards, digital menu boards, owner app, AI assistant, review manager — backed by Supabase and deployed on Vercel. It covers the full hospitality lifecycle: menu, ordering, payments, KDS, stock/costing, workforce/payroll, HACCP/operations, delivery (own-courier + aggregators), CRM/loyalty and reporting.

2.2 Architecture

A client-heavy SPA with a serverless backend. The React app renders a surface chosen by URL; state lives in a single store with multi-device coordination via BroadcastChannel + Supabase Realtime. The backend is Supabase — Postgres (system of record), Realtime, Storage, Auth and 60+ Deno Edge Functions that hold all third-party secrets and enforce tenant-aware authorisation (each function does its own auth: token + location-access checks). A native Android WebView APK wraps the app for Sunmi hardware with printer/reader bridges and self-updates from Storage. POS devices buffer writes in a durable offline queue and replay on reconnect, so a venue keeps trading through network loss with no data loss.

2.3 Multi-tenancy & data

Every operational row is scoped to a location_id. Isolation is defence-in-depth: (1) Postgres Row-Level Security on operational tables, with sensitive tables (delivery, aggregator, workforce PII) service-role-only and reachable only via edge functions; (2) edge-function authorisation — requireToken for operational reads the device needs, requireAccess (back-office user or super-admin) for management/mutations, always filtered by the caller’s location; (3) a client tenant fence that pins the active location. Two databases separate operational data from cross-company identity. Sales are immutable closed-check records; workforce audit and ledgers are append-only and hash-chained.

All credentials live server-side (edge env or per-tenant service-role-only columns, never returned to the browser); inbound webhooks verify a signature/secret and dedupe; outbound side-effects never block the customer’s payment; provider seams (dispatch_backend, processor) allow swapping vendors without UI change.

2.5 Payments & PCI

Card data is never handled by ServOS code — Stripe Terminal and Stripe/Ryft hosted/SDK flows tokenise on the processor; the platform stores only references (intent/session ids, amounts, processor last-4). This keeps PCI scope to the SAQ-A / A-EP class rather than handling card numbers. Money is computed in minor units and is unit-tested for penny-correctness (service charge, discounts, delivery surcharge, tronc/payroll).

2.6 Scalability & reliability

Stateless frontend on Vercel’s CDN; managed Postgres + Realtime. Concurrency hardening shipped: hot-path indexes, batched sync/print/replay, and reserve-then-act idempotency on courier dispatch (a unique index makes double-dispatch impossible across client + cron + retries). Offline-first POS: durable write queue, session reconciler, master/child heartbeat, print retry.

2.7 Deployment & release management

GitHub source with secret-scanning push protection. Push to develop builds the dev environment (active QA line); main is production. Edge functions deploy via the Supabase CLI; schema via reversible, numbered SQL migrations applied through the Management API on per-change authorisation. Every deploy bumps a single version source and adds an in-product changelog entry — an auditable, human-readable history of every production change.

2.9 Compliance & domain correctness (strengths)

  • UK VAT — per-rate tax with breakdowns on receipts; P&L on ex-VAT net sales; VAT treated as a liability.
  • Allergens — EU/UK FIC (“Natasha’s Law”) confirmation gate on declared-allergen orders, recorded to the order audit trail.
  • Payroll/tronc — server-side, penny-exact, tamper-evident (hash-chained), statutory holiday accrual; aligned to the UK Tipping Act / HMRC E24.
  • Age verification — Challenge 21/25 with audit log.

3 · Engineering methodology

  • Development model — trunk-style on develop (auto-deploys to the dev QA line); features delivered as small, reversible, end-to-end vertical slices (schema → data layer → edge function → UI → tests). Large features ship “build-now, go-live owner-gated”. Reuse-first.
  • Release process (every deploy) — version bump + plain-English changelog → build & tests green → push (Vercel) + edge-function deploy + numbered reversible migration (authorised). Edge functions that write new columns deploy after their migration.
  • Database change management — numbered reversible migrations with rollback blocks; additive-first; new sensitive tables are service-role-only by default; migrations applied only with explicit per-change authorisation.
  • Testing & quality — 150+ unit tests over pure business logic (tax, service charge, discounts, delivery surcharge/quote, courier time/lateness, waitlist, ops/HACCP, tronc/payroll); money pennies-correct. Substantial changes go through an automated adversarial multi-agent review (independent reviewers → verification of each finding) before deploy — which has caught real defects pre-production. Per-device training mode commits nothing (safe staff training on the live build).
  • Conventions & invariants — camelCase JS / snake_case SQL mapped both ways; static imports only; always resolve the real location_id before any write; never render an order object directly (serialise); new “complete order” paths must take payment first if money is owed.
  • Knowledge base — persistent in-repo docs (CLAUDE.md, DECISIONS.md, INVARIANTS.md, CURRENT_WORK.md) capture architecture, decisions, invariants and gotchas, read at the start of every work session.

## 1. Architecture in one paragraph

The Ryft integration is a **dual-processor seam**: `platform locations.payment_processor` (`'stripe' | 'ryft'`) routes every surface. Card-not-present (online/QR/kiosk-manual/gift/catering) uses **Ryft Payment Sessions + embedded SDK**. Card-present uses the **terminal_jobs pipeline**: the POS/kiosk mints a job row (ops DB), a **PAX A920 running the native `android/paxpay` app** claims it, collects the tip, then asks the server (`terminal-job-charge`) to initiate the charge at Ryft via the **In-Person REST API** — the device never holds a key or an amount. Settlement is processor-verified through ONE writer RPC (`terminal_job_settle_from_processor`), fed by session-verify, webhook, or human queue. A POS-side reconciler durably books the closed check. Almost the entire terminal_jobs layer (dispatch, mutexes, tip commit, settle, reconcile, pairing) is **processor-agnostic and should be kept**; only the ~200-line Ryft REST client and the calls into it need swapping for Adyen.

## 2. Shared Ryft client (the one thing everything else calls)

### `supabase/functions/_shared/ryft.ts` (200 lines) — **REPLACE with `_shared/adyen.ts`**
- Purpose: minimal Ryft REST client. Auth = raw API key in `Authorization`; sub-account via `Account` header; `Idempotency-Key` supported. Env: `RYFT_SECRET_KEY`, `RYFT_API_BASE` (sandbox default), `RYFT_PUBLIC_KEY`, plus `RYFT_WEBHOOK_SECRET` (used in ryft-webhook).
- Exports (→ Adyen equivalent must do):
  - `createPaymentSession` / `getPaymentSession` / `capturePaymentSession` / `voidPaymentSession` / `refundPaymentSession` → Adyen Checkout `/sessions` (or `/payments`), `GET` payment status via pspReference/webhook, `/payments/{psp}/captures`, `/cancels`, `/refunds`.
  - `createTerminalPayment(terminalId, {amounts, currency, settings.receiptPrintingSource, paymentSession:{platformFee, metadata, paymentSettings}})`, `cancelTerminalAction`, `getTerminal`, `confirmTerminalReceipt`, `refundTerminalPayment` → Adyen **Terminal API** (`SaleToPOIRequest` PaymentRequest to a POIID, `AbortRequest`, `TransactionStatusRequest`); Adyen prints/handles receipts itself, no confirm-receipt dance.
  - `createInPersonLocation`, `registerTerminal`, `listTerminals`, `deleteTerminal` → Adyen **Management API** (stores, `/terminals`, terminal assignment/ordering; Adyen terminals board themselves — no serial-number POST registration).
  - `createSubAccount`, `getAccount`, `createAccountLink`, `authorizeAccount` → Adyen **for Platforms**: legal entity + account holder + balance account + hosted onboarding link.
  - `listBalances`, `listPayouts(accountId)`, `listBalanceTransactions`, `listPlatformFees` → Balance Platform balances/transfers/payout reports.
  - `listDisputes`, `getDispute`, `acceptDispute`, `addDisputeEvidence(PATCH /disputes/{id}/evidence)`, `challengeDispute` → Adyen **Disputes API** (accept, supply defense documents, defend).
- Data written: none (pure HTTP client).

**Key semantic ports to re-verify for Adyen** (currently encoded as Ryft-isms in 4 places — terminal-job-charge, terminal-job-cancel, ryft-terminal-poll, ryft-webhook):
- `stateOf(status,lastError)`: Ryft has **no `Declined` status** — decline = `PendingPayment` + `lastError`. Adyen has explicit `Refused`/resultCodes; rewrite the mapper once, in one shared place.
- `cardOf(d)`: best-effort card block (brand/last4/auth_code/entryMode) for UK receipt rules → map from Adyen `additionalData` (cardSummary, paymentMethod, authCode, posEntryMode, AID, applicationLabel, CVM — Adyen actually supplies the AID/CVM fields the Ryft port leaves null).

## 6. Webhook + session-verify — **REPLACE transport, KEEP handling**

### `supabase/functions/ryft-webhook/index.ts` (412 lines)
- Auth: HMAC-SHA256 hex of raw body vs `Signature` header (`RYFT_WEBHOOK_SECRET`), constant-time-ish compare. Idempotency: upsert `event_id` into platform `ryft_webhook_events` (ignoreDuplicates → 200 duplicate).
- Handlers:
  1. `Account.*` → refetch account, `deriveStatus()` (capabilities/verification → charges_enabled/details_submitted), **auto-connect** by `metadata.location_id` → upsert `merchant_ryft_accounts`.
  2. `Dispute.*` → upsert platform `merchant_ryft_disputes` (respondBy deadline, recommended_evidence, raw) + **urgent merchant email** on `Dispute.created` (via send-receipt, resolves account email).
  3. `Payout.*` → touch `last_webhook_at`; failed/returned payout → merchant email.
  4. `PaymentSession.captured|refunded|voided` → `reconcilePayment()`: upsert platform **`ryft_payments`** ledger (amount, amount_refunded from re-fetched cumulative `refundedAmount`, status, channel, matched_closed_check, raw); match ops `closed_checks` by `stripe_payment_intent_id` **or** `payment_intents[].id` contains psId; **B1 backstop**: settle the matching `terminal_jobs` row via `terminal_job_settle_from_processor(source:'webhook')` (Captured→approved, Voided→declined; refunds never settle jobs); Ryft-dashboard refunds appended to `closed_checks.refunds` as delta with deterministic id `ref-ryft-<psId>-<cumulative>` + status partial_refund/refunded.

- Adyen equivalent must: verify Adyen's **base64 HMAC** notification signature; dedupe on eventCode+pspReference; map AUTHORISATION/CAPTURE/REFUND/CANCELLATION, ACCOUNT_HOLDER/verification, TRANSFER/payout-fail, CHARGEBACK/NotificationOfChargeback events onto the SAME five handlers; keep the ledger/backstop/gift contracts identical; **must return the `[accepted]`/200 fast** semantics. The `stripe_payment_intent_id`-as-generic-processor-ref convention on closed_checks carries over unchanged (it already holds Ryft ps_ ids).

Session-verify = `terminal-job-charge {action:'result'}` + `terminal-job-cancel`'s verdict read (§5.3): both settle via the ONE writer with `source:'session'` — the pattern (never settle from intent, always from the processor's answer) is the thing to preserve.

## 12. Decisions the plan must make (biggest first)

1. **Hardware.** Ryft in-person = PAX A920 + white-labelled STS controller, driven by our own paxpay app. Adyen runs **its own terminal estate + payment app**; the PAX A920s are almost certainly not reusable. Two shapes: (a) Adyen terminals driven cloud-side from `terminal-job-charge` (Terminal API) — kills the whole android/paxpay app, but also kills the bespoke Table-Pay-on-terminal UX and our tip screen (Adyen has native gratuity screens; Table Pay would need rebuilding on Adyen's POS-app options or moved to MPOS); or (b) keep a companion Android app on Adyen-compatible hardware. Everything in §5 survives either way; §7 survives only under (b).
2. **Sync vs poll.** Adyen's cloud Terminal API `/sync` blocks until tender completion — `terminal-job-charge` 'result', `ryft-terminal-poll`, and the device's 20s poll budget may collapse into one call + webhook backstop.
3. **Unknown-job recovery.** Adyen's status/lookup finally fills the marked gap in `terminal-job-reconcile` — schedule that as part of the migration, it removes the biggest operational runbook item.
4. **Pre-auth on POS terminals** becomes possible (TabPreAuthTerminal's `ryft_unsupported` branch → real Adyen hold).
5. **Fee model.** Ryft `platformFee` (markup on top; Ryft charges scheme fees to merchant via `paymentFees.combined.bookTo`) → Adyen splits/commission on the balance account. Confirm the commercial model before porting the markup arithmetic (it lives in 4 fns; extract into `_shared/adyen.ts` once).
6. **Transition rule** (already in the code): refunds/disputes route by the ORIGINAL payment's processor (`closed_checks.processor`, `gift_card_purchases.processor`). Ryft fns must stay deployed until the last Ryft-paid check ages out of refund/chargeback windows.
